## Selected synthesis: HOUSE as HOMEBASE, not dashboard

This is a **projection over existing owners**, not a new ontology:

```text
HOUSE      = HOMEBASE / exact place + addressed storage + service loci
ENV-0      = HARNESS / bounded body↔tool↔environment coupling
BODY/FIT   = LOADOUT BENCH / saved kits, mass, power, readiness, SET OUT

FOUNDRY    = fabricate / modify capability
DAYLINE    = current run / operation in time
HOUSEBUS   = private runtime truth + actuation
RETURN     = debrief / discrepancy / evidence / service residue
```

The key compression is:

```text
PLACE → STASH → PREP → FIT → SET OUT → USE → RETURN → SERVICE → READY
```

not:

```text
DASHBOARD → DEVICE LIST → MORE DASHBOARDS
```

### Inventory law

**CATALOG ≠ INVENTORY ≠ LOADOUT ≠ LOCATION.**

- **CATALOG**: known item/capability definitions; may come from Shopping/Foundry/reference data.
- **INVENTORY**: exact instances believed/observed to exist, each with source + current/last-known address.
- **STASH**: an addressed container or locus holding mobile inventory.
- **FIXTURE**: object whose useful identity is bound to a spatial locus unless explicitly released/moved.
- **LOADOUT**: temporary references to exact inventory instances selected for one purpose/friction profile. It owns no duplicate item state.
- **SERVICE**: returned residue such as low power, dirty, damaged, empty, misplaced, calibration due or unknown. Service state requires evidence; absence of telemetry stays UNKNOWN.

### ENV-0 law

ENV-0 is not the inventory database. It is the **mounting/coupling envelope** through which a selected loadout becomes embodied or room-coupled:

```text
STASHED OBJECT
→ LOADOUT REFERENCE
→ ENV-0 / BODY / CART / FURNITURE MOUNT
→ DEPLOYED
→ RETURNED
→ SERVICE / READY
```

That is already structurally compatible with HOUSE `BODY → HARNESS → OBJECT → ROOM → HOUSE → NETWORK` and BODY/FIT `LOADOUT → SET OUT → RETURN → PATINA → NEXT CUT`.

## POV / home-base interaction direction

Do not build a free-roaming 3D game around the house. On phone especially, prefer a **fixed locus / camera-tableau** model:

1. **Enter `/house/` at the current/selected room.** Spatial substrate stays visible.
2. **Look/select, do not navigate menus first.** A room, surface, container, fixture or carried object becomes the held locus.
3. The local aperture shows at most three truthful verbs derived from state and owner, e.g. `OPEN STASH`, `PREP LOADOUT`, `SERVICE / RETURN`.
4. **Direct station shortcuts remain available.** BODY/FIT, Shopping, Foundry, Dayline and Expert remain reachable without pretending spatial navigation is mandatory.
5. A homebase glance should answer only:
   - **WHERE AM I / WHAT LOCUS?**
   - **WHAT IS HERE / READY?**
   - **WHAT RETURNED DIFFERENT?**
   - **WHAT 1–3 MOVES ARE LAWFUL?**
6. Global exhaustive inventory lives in expert/search/atlas depth, not as the default room face.

### Useful room grammar

A room does not need a quest log. It needs a small set of spatially truthful roles:

```text
READY RACK   things deliberately kept near use
STASH        deeper storage / reserve
BENCH        configure / fit / fabricate / service
RETURN BIN   items back from use but not yet READY
FIXTURE      room-bound capability
PORT         route to another owner/runtime
```

These are roles over exact addresses; a physical basket, shelf, wall rail, trolley or cabinet may project one or more roles without changing canonical object identity.
