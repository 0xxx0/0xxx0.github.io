## 0. DISTILLED LINE

The strongest recovered donor is **not** “a universal geometry for the house.”

It is a physical systems discipline:

```text
few reusable parts
+ explicit joints / attachment interfaces
+ typed surfaces
+ typed flows
+ reversible configuration
+ analog/manual fallback
+ a configuration recipe
+ verification / RETURN
→ higher physical maneuverability without accumulating one fixed object per use
```

The current HOUSE should mine that discipline only where it reduces setup, teardown, duplicate hardware, or uncertainty.

## I1 — Replace “smart object” thinking with a small physical substrate vocabulary

Candidate HOUSE reading:

```text
POINT   = attachment / joint / anchor / connector
PATH    = bounded route carrying a typed flow
PLANE   = addressed surface or panel
POWER   = connectivity / sequencing / enabling relation
```

Important correction:

Do not use `PATH` as one untyped pipe.

A HOUSE path must declare its medium/function, e.g.:

```text
MECHANICAL_LOAD
POWER_DC
POWER_AC
DATA
AIR
WATER
LIGHT
SOUND
MOTION
HUMAN_ACCESS
```

This keeps the older abstraction while removing dangerous ambiguity.

## I4 — Analog-first is a strong HOUSE donor law

The historical source explicitly preferred mechanisms that remain useful without additional electronic energy.

Candidate HOUSE law:

> A physical interface should retain a useful manual/readable fallback when software, network, battery or automation disappears, unless the function intrinsically requires active control.

Examples of the principle:

- marks/indexes remain readable when sensors fail;
- a partition still partitions without Home Assistant;
- a latch still expresses safe/armed state physically;
- a rail/interface still identifies connection position without a UI.

This is compatible with HOUSEBUS/HA owning live device truth rather than replacing the physical object's local affordance.

This is relevant to HOUSE because the question is not merely “can this reconfigure?” but:

Use actual handling frequency before inventing permanent fixtures.

### O3 — Are POWER / PLANES / PATHS / POINT sufficient?

The old four-part decomposition may be useful but incomplete.

Candidate missing physical types:
- VOLUME;
- OPENING;
- TOOL;
- FASTENER;
- CLEARANCE;
- HUMAN BODY / ACCESS ENVELOPE;
- SERVICE;

### O4 — Is “POWER” the right name?

Historically it bundled loops/sequencing/connectivity and accessories.

For HOUSE it may be better decomposed into:
- CONNECTIVITY / TOPOLOGY;
- CONTROL;
- ENERGY.

Test before renaming.

### O5 — Does a typed PATH improve physical work?

A path abstraction only earns its place if it helps answer a real question such as:
- can this cable/air/water/load route coexist here?
- where can it bend?
- what blocks it?
- what must remain accessible?
- how is it detached/reversed?

Otherwise a plain annotated route is enough.

### O6 — When is a signed POLY port actually better than a named connector?

A simple label may beat `±X ±Y ±Z`.

Use signed ports only when orientation is recurrent, consequential and difficult to express plainly.

### O7 — Can configuration receipts be lightweight enough for daily physical work?

The donor becomes useless if each physical change requires documentation heavier than the change.

Candidate minimal RETURN:

```text
ID
before photo
parts
connection pattern
one key dimension
after photo
verifier
residue
```

This must come from observed recurrence, not enthusiasm for modularity.
