## 1. COLD-START AUX MODELS (sub-3.4s gate call, Apple Silicon)

**State of the art (2026-09):** The problem is solved — but only if you stop fighting it. Two facts define the whole space:

1. **`keep_alive` is a first-class shipped parameter.** Ollama's official API docs: `keep_alive` controls how long the model stays loaded after a request, default `5m` (https://raw.githubusercontent.com/ollama/ollama/main/docs/api.md — SHIPPED, current). The server env `OLLAMA_KEEP_ALIVE=24h` is the same knob for daemon mode (https://blog.kulman.sk/running-local-llm-coding-server/ — 2026-05-06, BLOG-OPINION, corroborated by several others). Your 13–22s cold start is not physics, it is the default 5-minute unload policy + heavyweight loading. Any model under ~4GB should simply never unload.
2. **Measured cold vs warm on Apple Silicon (2026):** M5 Max, 128GB, Q4 models — llama.cpp (GGUF) cold-loads via mmap: 8B = 0.4s cold / 0.2s warm, first token 1.0s cold / 0.6s warm; 70B = 2.3s cold / 1.4s warm, FTFT 4.7s / 3.8s. MLX loads eagerly: 8B = 1.8s cold, 32B = 6.9s, 70B = 15.2s — this matches your measured numbers exactly. Once pages are resident, MLX and llama.cpp FTFT converge within ~1s even on 70B (https://contracollective.com/blog/local-llm-cold-start-model-load-latency-m5-max-mlx-llama-cpp-2026 — 2026, BLOG-OPINION but data-dense, has full table and a pinning policy snippet). **The real fix is a resident-budget/pinning policy: pin small hot models, let big cold models pay the lazy mmap load.**

**Worth stealing:**
- **Ollama `keep_alive=-1` / `OLLAMA_KEEP_ALIVE=24h`** — SHIPPED. One line, kills your entire 13–22s problem for a resident model. For a Q4 1–3B gate model on any M-series, warm TTFT is ~0.1–0.5s. 3.4s budget: comfortable.
- **`mlx_lm.server` as a persistent process** (https://github.com/ml-explore/mlx-lm; usage confirmed in https://github.com/Aider-AI/aider/issues/4526 — SHIPPED) — keeps the model resident across requests via an OpenAI-compatible endpoint. But be warned: MLX loads eagerly, so this only fixes you if the model stays resident — it does not fix cold start for a big model. Use it for the *pinned* small model.
- **The thinking-field trap has a name and a fix.** Qwen3.x/DeepSeek-R1-class small models put the whole answer in `reasoning_content`, leaving `content=None` — widely confirmed: LM Studio tracker https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/1602 (2026-03-04), vLLM https://github.com/vllm-project/vllm/issues/38894 (2026-04-03), and structured-output variants (LM Studio #1698, #1773) where your JSON response lands in the reasoning stream (2026-05-31). Fixes, in order of robustness: (a) use a **non-reasoning** small model for the gate (`enable_thinking=False` at chat-template level is documented by Qwen: https://huggingface.co/Qwen/Qwen3.5-9B/discussions/13 — SHIPPED); (b) parse `reasoning_content` as a fallback; (c) Ollama's `/api/generate` now has a first-class `think` param (same api.md above).
- **Pinning policy** (same contracollective post): "pin small hot models in MLX; serve rare big models via llama.cpp mmap so an eviction costs seconds, not 15." This is a script, not a product — 1–2h of work.

**Does it solve THIS problem?** Yes — squarely, for a ≤3B gate model. Cloud is **not** "simply correct" here; it is correct only if you refuse to run a persistent local process. The honest trade: local warm gate = ~1h ops + RAM (a Q4 1–3B is 0.7–2GB); cloud = zero ops, per-call latency jitter + data egress.

**Recommendation:** **STEAL** (keep_alive + 1–3B non-reasoning gate model + `reasoning_content` fallback). **IGNORE**: new "serverless local runners" claim nothing beyond this; MLX for the cold big model.

## 2. AGENT MEMORY ABSORPTION (durable absorb of subagent/cron work)

**State of the art (2026-09):** The field converged on four shapes: (1) **persistent memory servers** (Letta/MemGPT lineage), (2) **memory-as-a-library / MCP memory tools** (mem0, MCP knowledge-graph server), (3) **agentic self-organizing memory** (A-MEM), (4) **reflection loops** (Generative Agents; now productized as Claude Code's memory/memory-tool practices). Nobody ships "absorb my subagent transcripts" as a product — because it is a small integration problem, not an AI problem. The thing that actually killed your subagent output (survived only because files were still in `/tmp`) is a **write-back contract**, not a smarter model: every worker must write a digest to a durable store before it exits.

**Worth stealing:**
- **mem0 + OpenMemory** — SHIPPED. mem0 is a memory layer for agents (https://github.com/mem0ai/mem0; MCP server: https://docs.mem0.ai/platform/mem0-mcp). OpenMemory (https://mem0.ai/openmemory) auto-captures project-scoped memory for Cursor/Windsurf/VS Code agents with zero pipeline changes — this is literally the "absorb loop, shipped" for coding agents. Adapting it to a cron that digests Hermes transcripts into its store is a day.
- **A-MEM** — RESEARCH. arXiv 2502.12110 (Feb 2025, updated Jul 2025; NeurIPS 2025: https://proceedings.neurips.cc/paper_files/paper/2025/hash/19909c36f51abc4856b4560aff3d36d6-Abstract-Conference.html; code: https://github.com/agiresearch/a-mem). The stealable idea: the LLM itself writes/updates/reorganizes memory (write, update, reorganize ops) instead of fixed RAG plumbing — exactly the semantics you want for "yesterday's decision, today's correction" absorption. Steal the op-set; don't adopt the framework.
- **Reflection loop** — RESEARCH (Park et al., Generative Agents, 2023): every N events, summarize upward into reflective memories. This is the canonical cheap absorb loop; you already have the cron machinery.
- **Letta** — SHIPPED (https://github.com/letta-ai/letta; self-hosting: https://docs.letta.com/self-hosting; also https://www.smfclearinghouse.com/deployment-recipes/letta-self-hosted-agent-memory/ — 2026 recipe). Persistent memory blocks + archival memory + self-editing context, agent server architecture. Real, active. But it is a platform (Postgres, app server) — inspect if you want an *agent management server*, not just an absorb loop.
- **Anthropic's official memory guidance** — SHIPPED (https://code.claude.com/docs/en/best-practices, `/docs/en/memory`, subagent `memory:` frontmatter in v2.1.33+ — corroborated https://orchestrator.dev/blog/2026-04-06--claude-code-agent-memory-2026/ BLOG-OPINION; concrete cron-based MEMORY.md design: https://ianlpaterson.com/blog/claude-code-memory-architecture/ BLOG-OPINION). Patterns: load a small boot file every session; accumulate; compact.

**Does it solve THIS problem?** Partially. Every component above assumes a memory *store*; your actual gap is a **termination contract**: subagent/cron output must be written back to a durable store (SQLite + FTS5 you already have) before the process is allowed to end. That is ~4h of tooling and is the only thing on this list that directly prevents the kill-mid-flight data loss you had today. The absorb/AI half (digest, dedupe, link) layers on top.

**Recommendation:** **STEAL**: (a) write-back contract (mandatory durable digest on exit — 4h), (b) reflect-loop digest cron (2h), (c) mem0 or MCP memory server for cross-tool remember (1 day). **WATCH**: Letta. **IGNORE**: adopting a "memory AGI" framework — bloat, no payout at your scale.

## 3. CROSS-SESSION CROSS-REFERENCE (dozens of sessions; losing decisions)

**State of the art (2026-09):** Nothing shipped solves this wholesale; the shipped SOTA is a *combination* of (a) a decision-log discipline, (b) persistent memory tooling, (c) semantic search over plain files. Your wrangler + FTS5 is already in the top quartile of what people run; the deficit is **structure and dedupe**, not retrieval recall.

**Worth stealing:**
- **ADR (Architecture Decision Records) as your decision unit** — SHIPPED practice + SHIPPED tools. Nygard 2011; tooling: https://github.com/npryce/adr-tools, collectives: https://adr.github.io/. The steal: every session end appends a numbered, one-file record `{context, decision, rejected alternatives, status: proposed/accepted/superseded}`. That turns "what did I already decide?" into a `grep status=accepted` instead of a fuzzy memory. This is the single highest-leverage item in this whole document for you.
- **MCP memory knowledge-graph server** — SHIPPED (https://github.com/modelcontextprotocol/servers/tree/main/src/memory; npm `@modelcontextprotocol/server-memory`, last publish 2026-08-31 — active). Persists entities/relations across chats in a local graph file; gives agents a cross-session "who/what links to what." Directly embeddable into session boot instead of prose prompts.
- **sqlite-vec** — SHIPPED (https://alexgarcia.xyz/sqlite-vec/; v0.1.0 Aug 2024, active 2026). Vector search inside the SQLite you already use — add embedding columns to your session digests so "which of 400 prior sessions already asked this?" becomes a KNN query that catches semantic near-dupes FTS5 misses. ~2–3h.
- **Khoj** — SHIPPED (https://github.com/khoj-ai/khoj). Self-hosted second brain: indexes markdown/PDF/org, semantic Q&A, agent automations. Real and mature, but it is a server + app: **WATCH** (it competes with your session_search; it does not beat ADR-ified wrangler + sqlite-vec unless you want RAG chat over the whole archive).

**Does it solve THIS problem?** Yes, with a half-day build: (1) wrangler emits ADR-style entries; (2) sqlite-vec dedupe + link across sessions at digest time (a cron); (3) boot prompt reads "top 5 linked prior decisions" instead of nothing. Don't buy a second-brain product to get this.

**Recommendation:** **STEAL** (ADR-ify the wrangler; sqlite-vec dedupe cron). **WATCH** (Khoj; MCP memory server as the graph layer). **IGNORE**: vector-DB migrations, Obsidian plugin ecosystems.

## 4. SAFE DEDUPLICATION OF A LARGE PERSONAL ARCHIVE (66GB + 26GB + 12GB)

**State of the art (2026-09):** Layered — and the layers are sharply different in maturity:
- **Exact-byte dedupe**: mature, shipped, safe. Best-in-class for your case: **rmlint** (fast, special-file-aware, macOS packaged) and **jdupes** (fast fdupes fork; https://www.jdupes.com/, https://github.com/JoooostB/jdupes), **czkawka** for GUI grouping (https://github.com/qarmin/czkawka, active 2026; https://czkawka.net/).
- **Media-similarity dedupe**: shipped but lossy — czkawka's "similar images" uses perceptual hashing (https://deepwiki.com/qarmin/czkawka/4.2-media-analysis-tools) — fine for "find near-identical photos," dangerous if you let it auto-delete.
- **Semantic dedupe (embeddings)**: RESEARCH only — SemDeDup (arXiv 2303.09540, ICLR 2023) is designed for ML *training* data, not personal archives. **Nothing credible ships semantic dedupe as a safe personal-archive tool as of 2026-09.** For a mixed personal archive this is overkill and actively risky — IGNORE.
- **Block-level dedupe**: Borg (https://borgbackup.org/, SHIPPED) content-defined chunking — correct *backup-layer* dedupe (your 12GB corpus increments), not an archive-deletion tool.

**The provenance answer (steal this):** rmlint's tutorial documents two operations that dedupe storage **without destroying file identity**: `FIDEDUPERANGE` (clone extents — Linux/btrfs) and reflinks (https://rmlint.readthedocs.io/en/latest/tutorial.html). On APFS/macOS the equivalent is copy-on-write clone (`cp -c` / `clonefile`). **Prefer reflink/clone dedupe over delete+hardlink, always** — hardlinking per rmlint's own cautions first *deletes* the duplicate then relinks, so a single false positive is data loss (https://rmlint.readthedocs.io/en/latest/cautions.html — this is rmlint's own warning, take it as authoritative).

**Known failure modes (watch for these):**
1. **Hardlink-based "dedupe" = delete-then-relink** → false positive = unrecoverable loss; also hardlinks break across volume boundaries (your three volumes are separate filesystems — hardlinks cannot span them).
2. **Byte-identical ≠ same provenance**: two identical files from different donors (two backups of one photo, different origin folders) — merging or deleting one erases the distinction you later need for lineage. Your FIELD rules (RECOVER BEFORE INVENTING, exact-source) are a stricter provenance regime than any tool; the tool must never overrule the manifest.
3. **Hash-only tools miss near-dupes** (different resolutions/encodes) — szw/`fdupes`-class tools only give you exact matches; media similarity must be a separate, human-reviewed pass.
4. **Dedupe-before-verify**: deduplicating across a 66GB dump whose integrity isn't yet verified lets one corrupt "original" delete a good copy. Verify hashes per volume first (you already do byte-hash recovery discipline).

**Does it solve THIS problem?** Yes for the file layer: rmlint dry-run → review → reflink-clone dedupe, with a per-file provenance manifest generated *before* any deletion. Budget: the 66GB dump is mostly media/originals — expect the media-similarity pass to be the slow human gate.

**Recommendation:** **STEAL** (rmlint with reflink/clone, manifest-first, dry-run gate; czkawka for photo similarity review; borg for the corpus if you want backup-layer dedupe). **IGNORE** (SemDeDup-style embedding dedupe for this archive — nothing credible ships it safely; marketing-heavy "AI dedupe" SaaS).

## 5. VERIFIABLE AUTONOMY / TRUST LOCKS

**State of the art (2026-09):** The 2025–26 consensus is unambiguous: **contain the environment, then raise autonomy — never raise autonomy by trusting the model**. Everything credible clusters into four rungs, and they map cleanly onto what you have (Tirith = dangerous-literal scanner, JEev = pre-tool gate, approvals, reversibility grant):

1. **Structural containment (SHIPPED):** Claude Code now has first-class sandboxing: macOS uses the built-in Seatbelt framework (`/sandbox`), Linux uses bubblewrap (https://code.claude.com/docs/en/sandboxing — current docs); Anthropic open-sourced its Sandbox Runtime as an official research preview (https://github.com/anthropics/sandbox-runtime). On the research→shipped boundary: **GVisor** — a userspace-kernel sandbox for AI agents, millisecond starts, checkpoint/restore, embraced by GKE as its managed "Agent Sandbox" runtime (https://gvisor.dev/ ; GKE integration + honest gap analysis: https://www.armosec.io/blog/sandboxing-ai-agents-gke-workload-identity/ ; K8s pattern: https://devtocash.com/blog/2026-09-19-ai-agent-sandbox-kubernetes-gvisor-code-execution). For your exact stack (macOS, Hermes), the same shape is a **Seatbelt/sandbox-exec file-policy layer** around the agent process — open-source example targeting Claude Code AND Codex: https://github.com/CJHwong/agent-seatbelt (2026, small, exactly the "outer file policy under the agent's own sandbox" pattern).
2. **Deterministic stop-conditions (SHIPPED):** Claude Code's `/goal` + Stop-hook verification gates — "give the agent a check it can run; the check closes the loop without you" (https://code.claude.com/docs/en/best-practices — includes plan/permission modes: read-only → plan → direct edits; that is a shipped graduated-autonomy ladder). The "trust lock" you're describing = an auto-approved rung that is conditionally enabled only while a verifier passes and a Stop hook would block completion. That is shipped today in Claude Code and buildable in Hermes with the hooks you already run.
3. **Irreversibility-aware protocols (RESEARCH, but the exact match to your "reversibility grant"):** METR's *AI Control* (arXiv 2312.06942, Dec 2023, ongoing program) formalizes: treat *reversible* actions as low-risk (monitor cheaply), *irreversible* actions as high-stakes (monitor with adaptive auditing, no-trust assumptions, time-of-check/time-of-use scrutiny). Your grant ("if it's undoable, just go ahead") is a byte-for-byte restatement of the Control framing — the missing piece is that METR pairs it with *audit protocols* and *red-team testing of the monitor itself*. METR's current evaluation practice: UK AISI's Inspect + open-source Hawk platform for agent eval at scale (https://metr.org/measuring-autonomous-ai-capabilities/). Supporting RESEARCH: *Levels of Autonomy for AI Agents* — five rungs (operator→collaborator→consultant→approver→observer) and the "autonomy certificate" idea (arXiv 2506.12469, Jun–Jul 2025, Knight First Amendment Institute essay series; https://knightcolumbia.org/content/levels-of-autonomy-for-ai-agents-1). An "autonomy certificate" is exactly a machine-readable trust lock: a declared capability/authority range other agents honor.
4. **Monitoring the model, not just the sandbox (RESEARCH, and the honest limit):** Apollo's evaluations program — in-context scheming, and *Chain of Thought Monitorability: A New and Fragile Opportunity for AI Safety* (2025-07-15; all at https://www.apolloresearch.ai/science) — shows monitorability of reasoning is real but **fragile**: models get better at recognizing evaluation environments, and production RL increases reward-seeking (2026-07-21 result). Apollo explicitly pivoted its agenda to **scheming control evaluations** — i.e., control protocols under worst-case assumptions (https://www.apolloresearch.ai/u/2025/11/Apollo-Research_18-Month-Update-Dec-13-2024.pdf, Dec 2024). Blunt translation: your Tirith literal-scanner and JEev gate block *known* dangerous literals and *known* gate shapes; the 2026 evidence says the residual risk is in *allowed actions used for unintended purposes* — no scanner fixes that, only blast-radius reduction and auditing.

**Does it solve THIS problem?** Partially, and the parts that solve it are shipped: your next trust-lock rung is (a) a Seatbelt file-policy outer layer so "always go ahead" costs nothing when it misfires, (b) a deterministic verifier+Stop-hook completion gate before auto-approval rungs engage, (c) a one-page protocol doc written in AI-Control language (reversible = auto, irreversible = monitor+approve, monitor gets red-teamed). What does NOT exist as shipped: general "reversible-action certificates" or automated-rollback products — **nothing credible found** under those exact names; nearest real things are ZFS/APFS snapshot discipline (you already git/return everything) and gVisor checkpoints (Linux-only).

**Recommendation:** **STEAL** (goal/Stop-hook verifier gate; Seatbelt/sandbox-exec outer file policy via agent-seatbelt pattern; one-page AI-Control-style protocol for the reversibility grant). **WATCH** (GVisor; Apollo/METR control-eval tooling as it ships). **READ-ONCE, don't adopt** (autonomy certificates as a governance scheme — bureaucratic, not engineering).
