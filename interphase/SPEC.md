## Refined request

Recover the actual Code-folder prototypes, images and FU/INTERPHASE lineage. Restore

entry surfaces. Carry useful mechanisms forward into the existing native tools, then
prove one meaningful task across representations before promoting another general

The operator should be able to resume, understand the relevant constraints, change
something that matters, see the consequence and return without rebuilding context.
Use their existing names and references. The worker translates informal intent;
the operator does not maintain our architecture or packet vocabulary.

Assumptions: keep the existing repository and native state owners; ordinary text and
lists remain usable; experimental optics are optional; no archive deletion or broad

is unresolved. Recovered FU5X2 is a verified historical artifact, not a claim to have
found that latest image. Earlier assistant delivery claims are not user endorsements.

## Why the previous work went backwards

We substituted an implementation property (shared source/cursor state) for the actual
job. We tested the abstraction we had chosen, then treated passing as evidence that
the choice was right. The 0.10 reader preserved text accurately while replacing the
entry, route recognition and native work. The recovered workbench's default edits a
route's title/description; that is still not editing a room, a day's work or a source
argument. More projections of the wrong object make the mismatch more expensive.

The earlier Forward Field 1.2 UX review had already identified the same failure:
architecture exposed as navigation, ordinary tasks requiring RUN ceremony, duplicate
centers, useful LIST demoted, FIELD becoming another destination. We failed to apply
that finding. The repair starts by restoring access, not by adding a fourth framework.

## The actual unification target

Unify **continuity and access to operations**, not all domain models or all layouts.
The same address/selection should reach its native model and available operations.
A representation earns its place by exposing a relevant relation, constraint or
manipulation more effectively. A room's geometry, a day's time constraints, and a
text's exact ranges remain different data. Their useful commonality is a recoverable
object and an honest action boundary, already present in the host contracts.

Apply `control/REPRESENTATION.json`, `control/QA.json` and the existing
`control/INTERPHASE_MAPPING_CONTRACT.json`; do not replace them with new theory.
For a named task, test whether two states that look alike still need different next
moves or produce different relevant consequences. If so, show the missing distinction
or leave that operation in its native view. Shared appearance and reversible view
switches do not prove control equivalence. Spatial arrangement must state what angle,
distance, adjacency and depth actually mean. A generic 3D room of metadata cannot
stand in for the geometry or constraint model being operated on.

A useful end state could be an ordinary page with an optional focus/aperture tool:
read the list, hold an actual object, expose its relevant local relations, manipulate
it in its owner, return. The existing room branch is the candidate for investigating
that direction. This is a hypothesis to test, not a promise that spatial display is
better. Keep the surprising representation when it makes a formerly difficult
operation easy; keep the list where it wins.

## Validation and practical limits

Local checks cover syntax, FIELD operations/reversibility, document integrity,
CURRENT/manifest versions and release consistency. The existing browser suite now
starts with the ordinary entry task at three widths, checks that experimental reader
code is not requested, then runs the explicit reader's existing round trips. Existing
native map and workbench proofs remain separate. Exact candidate CI is authoritative
for browser results; an assertion written here is not a passing result. Human daily
use and the spatial/dayline work packages remain unproved.

No broad archive has been removed or reorganized. The new behavior is an additive
correcting commit and can be reversed through Git. Restoration is not presented as
the novel useful instrument the operator ultimately requested; it removes a regression
and supplies an evidence-grounded path to that instrument.

## Research used to change the method

- Bret Victor, [Magic Ink](https://worrydream.com/MagicInk/): design the information
  needed for the task before inventing navigation. Its information-software argument
  does not remove the need for manipulation in an operating tool.
- Green and Blackwell, [Cognitive Dimensions tutorial](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf): assess the activity profile, visibility,
  hidden dependencies, viscosity and premature commitment. These are tradeoffs, not
  a proof of one universal interface.
- Beaudouin-Lafon, [Instrumental Interaction](https://www.lri.fr/~mbl/papers/CHI2000/):
  a relevant primary research direction for reusable instruments acting on domain
  objects. The indexed abstract was retrieved; the full paper timed out in this run.

The practical consequence is a task comparison and an action on the actual domain
object. More diagrams, theories or successful transport checks cannot substitute.
